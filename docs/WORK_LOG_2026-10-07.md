## 1. 競合検出の修正

### 1.1 問題

`apply_editor_json.py` の `current_value()` / `latest_edit_act()` だけが、
§5.3 で確立した `prov:generatedAtTime` ではなく**グラフ IRI の文字列ソート**で
最新を判定していた。読み取り側（`latestGraphOnly()`）とは別系統になっていた。

グラフ名は `{edcsId}/{種別}/{日付}` の順で、**種別が日付より先に来る**。
文字列降順では `edcs` > `claude` が優先される。

実測（EDCS-25501631、ORDER BY のみ差し替え）:

| 順位 | 旧 `DESC(STR(?g))` | 新 `DESC(?t)` |
|---|---|---|
| **1（採用）** | **`edcs/2026-01-15`**（最古） | **`claude/2026-05-03`**（最新） |
| 2 | `claude/2026-05-03` | `claude/2026-04-30` |
| 3 | `claude/2026-04-30` | `edcs/2026-01-15` |

**旧実装は最古のグラフを「現在値」として採用していた。**
`/editor/` を優先する分岐があったため校訂同士の連鎖は正しく動いていたが、
機械グラフ間の判定が読み取り側と食い違う状態だった。

### 1.2 `latest_edit_act` — 人手校訂の識別子

`/editor/` フィルタを外すにあたり、何で人手校訂を識別するかを実データで確認した。

| 候補 | 可否 | 実測 |
|---|---|---|
| グラフ名 `/editor/` | △ | 文字列依存。これを無くすのが目的 |
| `hmkia:generatedBy` の有無 | **✗** | EntityReference は 0 件だが**Statement には機械抽出が付与** |
| act の型 `InterpretationUpdateAct` | **✗** | LLM の enrich も同じ型（112,378 件） |
| **agent の型 `hmkia:HumanAgent`** | **✓** | `SoftwareAgent` 2 件、`HumanAgent` 0 件で分離 |

当初 `hmkia:generatedBy` の有無で足りると考えたが誤りだった。
そのまま実装していれば、**未校訂の Statement が LLM の抽出 activity に対して
`hmkia:revises` を張る**偽の来歴を生むところだった。

### 1.3 日付を持たないグラフ

`COALESCE(?t, "")` により最下位に落ちる（Fuseki で実測確認）。
除外ではなく最下位としたのは、日付不明でも値がある以上は競合検出が働くべきだから。

## 3. EntityReference の来歴 — 設計上の制約

### 3.1 機械更新には版が存在しない

`enrich_divinity`（47,204 act）や `enrich_vital_events`（47,204 act）は
PersonReference の属性を書くが、RDF 生成時には**JSON の最終状態を1回出力するだけ**で、
Statement のような `_v0`/`_v1` 分岐がない。

実測:

```
person/0 isDivinity=false | generatedBy= None   (claude/2026-04-30)
person/0 isDivinity=false | generatedBy= None   (claude/2026-05-03)
```

enrich が付けた値なのに `hmkia:generatedBy` が付かない。
**どの属性が extract 由来でどれが enrich 由来かが RDF 上で区別できない。**

### 3.2 グラフの日付も実態とずれている

グラフ URI の日付は `_extract_act()` が返す **extract の日付**で決まる
（[create_rdf_himiko.py:1202-1204](../pipeline/provenance/create_rdf_himiko.py#L1202-L1204)）。
enrich の日付は使われない。

| | 時刻 |
|---|---|
| グラフ `claude/2026-05-03` の `generatedAtTime` | 2026-05-03T09:25:48Z |
| 実際の `enrich_divinity` 実行時刻 | 2026-04-23T13:23:44Z |

enrich は必ず extract より後に実行されている（53,513/53,513 件）にもかかわらず、
グラフ名は extract 時点で固定される。

### 3.3 act の型と実装の不一致

**enrich は CreationAct ではなく、すべて UpdateAct である**（当初の想定と異なる）。

| hasType | OWL クラス | 件数 |
|---|---|---|
| `extract` | CreationAct | 580 |
| `reextract_relationships` | CreationAct | 19,159 |
| `scrape_edcs` | CreationAct | 1 |
| `enrich_*`（7 種） | **UpdateAct** | 112,378 |
| `schema_fix` | UpdateAct | 2 |
| 人手校訂 | UpdateAct | 0（未運用） |

境界は「enrich / 人手」ではなく「初回生成 / 既存リソースの更新」。
人手校訂が UpdateAct なのは enrich と同じ側に属するため。

オントロジーの `InterpretationUpdateAct` の定義は
「新しい URI を持つ別インスタンスとして生成され `prov:wasRevisionOf` で前版を参照する」
と規定するが、実装は三者三様:

| 対象 | 定義どおりか |
|---|---|
| enrich → Statement（cost, location, recipients） | ✅ `_v1` + `wasRevisionOf` |
| enrich → **EntityReference**（divinity, vital_events） | ❌ **新 URI も `wasRevisionOf` も無い** |
| 人手校訂 → EntityReference | △ グラフを分け `revises` で連鎖 |

**`enrich_divinity` と `enrich_vital_events`（計 94,408 act、全 UpdateAct の約 84%）が
UpdateAct を名乗りながら規定を満たしていない。**
オントロジーの不備ではなく生成コードの未実装。

なお `hmkia:generatedBy` の定義は対象として EntityReference を明示的に挙げ、
domain を限定していないため、付与すること自体はスキーマ上まったく問題ない。

### 3.4 再実行で解釈が変わった事例は 14 件

パイプライン3段階で同一 `edcs_id` を突き合わせて調査（`_provenance` の activity は
同型を置換する実装なので、件数ではなく**タイムスタンプの差**で再実行を判定）。

| 項目 | 件数 |
|---|---|
| `validated_career_graphs` で同一 edcs_id が複数回出現 | 4,846 |
| うち `enrich_divinity` のタイムスタンプが異なる（真の再実行） | **4,649** |
| 再実行で生じた属性差分 | 25 |
| うち空→値の初回補完（履歴の損失なし） | 11 |
| **うち値→別の値（真の再解釈）** | **14** |

実例（`EDCS-25401734` person/3 "Nerva"）:

| 実行 | モデル | divinity | 判断理由 |
|---|---|---|---|
| 2026-04-24 | sonnet-4-5 | **True** | "divi Nervae"（神格化されたネルウァ）への言及 |
| 2026-05-11 | sonnet-4-6 | **False** | "divi Nervae **abnepoti**"（神君ネルウァの来孫）＝碑文の対象は子孫 |

**後の実行の方が正しい。** 属格 + `abnepoti` の構文を2回目で正しく解釈した。
モデル更新で解釈が改善した実証例であり、論文で言及する価値がある。

**重要**: この 14 件の旧値は**現状でも Fuseki に残存している**。
extract 日付が異なるため偶然別グラフになったため（§6 で残置した重複グラフ）。
失われているのは「どの act がその値を書いたか」の対応だけ。

## 4. 案E（グラフ層化）の試験実装 — 不採用

### 4.1 案の内容

「人手校訂と同じ構造で enrich も記述する」。
act ごとに名前付きグラフを分け、その act が書いた属性だけを入れる。
グラフ名は extract 日付ではなく**その act の実行時刻**。

enrich と人手校訂の違いは3点のみになる:

| | enrich | 人手校訂 |
|---|---|---|
| グラフ | `/{act種別}/{実行時刻}` | `/editor/{実行時刻}` |
| act の型 | `InterpretationUpdateAct` | **同じ** |
| `hasType` | `"enrich_divinity"` | `"manual_edit"` |
| agent | `hmkia:SoftwareAgent` | `hmkia:HumanAgent` |

### 4.2 試験実装

[prototype_layered_entityref.py](../pipeline/provenance/prototype_layered_entityref.py)
（試験専用、パイプライン未組み込み）。
`generated_fields` から「どの act がどの属性を書いたか」を引いて層を分ける。

一時データセット `proto_layered` を作成して検証し、削除済み。本番は無変更。

### 4.3 動作：成功

`EDCS-25401734` で層が正しく分離され、再解釈の両版が残ることを確認:

```
2026-04-24T20:55:24Z | isDivinity= true   (enrich_divinity/20260424T205524Z)
2026-05-11T21:25:50Z | isDivinity= false  (enrich_divinity/20260511T212550Z)
→ プロパティ単位クエリの結果: false  ✓
```

### 4.4 発見した欠陥 — null が過去の値を消せない

同じクエリで `divinityType` は **`"Nerva"` を返す**。
しかし 05-11 の act は「神格ではない」と判断しており `divinityType` は null。

**層化方式では「書かなかった」と「存在しないと判断した」が区別できない。**
05-11 の層に `divinityType` のトリプルが無いため、04-24 の値を上書きするものがない。

結果として矛盾した組み合わせが生じる:

```
isDivinity   = false   (05-11 の判断)
divinityType = "Nerva" (04-24 の判断)
```

現状の「1グラフに全部書く」方式では、新しいグラフに無いこと自体が削除を意味するので
この問題は起きない。対処には tombstone か「act が扱う属性群」の宣言が必要で、
案Eの複雑さをさらに増やす。

### 4.6 評価と結論

## 4.9 校訂の書き戻し経路が存在しない

作図の過程で判明した**未解決の構造的欠落**。実害はまだ出ていない（校訂 0 件）が、
運用開始前に方針を決める必要がある。

### 4.9.1 事実

| スクリプト | Fuseki を読む | Fuseki に書く |
|---|---|---|
| `enrich_career_graphs.py` | ✗ **JSON を読む** | ✗ |
| `create_rdf_himiko.py` | ✗ | ✗（TriG を出力するだけ） |
| `apply_editor_json.py` | ✓ | ✓ |

**校訂を JSON 側に戻す経路が存在しない。** `apply_editor_json.py` が
Fuseki に触れる唯一のスクリプトであり、パイプラインの上流は校訂を認識しない。

### 4.9.2 何が起きるか

校訂後に enrich → 再投入を行うと:

1. JSON は校訂を知らないまま enrich される
2. `create_rdf_himiko.py` が新しい `claude/{日付}` グラフを生成
3. 再投入すると、editor グラフは**残るが**再投入の方が `generatedAtTime` で新しくなる
4. → **校訂が読まれなくなる**（グラフは残るので復旧は可能）

さらに `enrich_career_graphs.py:189` は `if 'divinity' not in person` のように
**既に値があればスキップ**する設計のため、校訂が JSON に反映されていれば
その仕組みがそのまま校訂の保護として働くが、現状はそうなっていない。

### 4.9.3 選択肢（**案1を実装 → §4.10**）

| 案 | 内容 | 評価 |
|---|---|---|
| **案1** | `export_corrections_to_json.py` を作り校訂を JSON に書き戻す | **推奨**。JSON が正本になり、既存のスキップ処理が校訂保護として機能する |
| 案2 | enrich 前に Fuseki から校訂済みフィールドを取得し除外 | JSON と Fuseki の二重管理になり正本が曖昧 |
| 案3 | 読み取り時に editor グラフを無条件優先 | 修正前の `current_value()` に近い挙動。機械の再解釈が優れる場合を排除してしまう |

### 4.9.4 残る論点 — 校訂済みフィールドを再判断させるか

案1を採っても、次の問いは残る:

| 方針 | 利点 | 欠点 |
|---|---|---|
| 校訂は不可侵 | 人手の判断が確実に残る | モデル改善の恩恵を受けられない |
| LLM に再判断させ相違時に警告 | 改善を取り込める | 校訂が静かに覆る危険 |
| 校訂内容をプロンプトで LLM に渡す | 人手の根拠を踏まえた判断 | 実装が複雑、コスト増 |

§3.4 の Nerva の例（sonnet-4-6 が `abnepoti` を正しく読んだ）が示すとおり、
**後の機械判断が人手より優れることは実際にある**ため、
「人手が常に正しい」という前提は置けない。

## 4.10 案1の実装 — `export_corrections_to_json.py`

[export_corrections_to_json.py](../pipeline/provenance/export_corrections_to_json.py) を新規作成。
Fuseki の editor グラフから校訂を取得し、career graph JSON に書き戻す。

### 4.10.1 動作

1. `hmkia:HumanAgent` が実施した act が生成した値を取得（`apply_editor_json.py` と同じ判定）
2. 同一プロパティが複数回校訂されていれば**最新のみ**を採用
3. subject URI から JSON 内の対象を特定し、該当フィールドを更新
4. `_provenance.activities` に `manual_edit` act を追加

### 4.10.2 設計上の要点

**URI → JSON の対応付け**:
`mk/{id}/career/{i}` の `i` は人物を跨ぐ通し番号で、各人物の `career_path` は
`order` でソートされてから採番される。`_career_entries()` はこの走査順を
`create_rdf_himiko.py` と同一に再現している。ここがずれると別の職位に書き込む。

**`manual_edit` act はリスト先頭に挿入**:
`_act_uri_for_field()` は**最初に**該当フィールドを宣言した act を返す。
extract がほぼ全ての人物フィールドを宣言しているため、末尾に追加すると
校訂値が extract の産物として記録されてしまう。実測で確認・修正した。

### 4.10.3 実装中に発見・修正した不具合

## 4.11 値の履歴の保存 — `value_history` と history グラフ

§4.10 の実装には**旧値が失われる**欠陥があった。実測で確認した経緯と対処。

### 4.11.1 発見した問題

書き戻しは `target[field] = new_value` の破壊的代入で、旧値は JSON から消える。
グラフ名は `_extract_act()` が extract 日付から決めるため（[create_rdf_himiko.py:190-197](../pipeline/provenance/create_rdf_himiko.py#L190-L197)）、
**校訂しても同じグラフ名のまま中身だけが変わる**。

実測（書き戻し → RDF 再生成）:

| | 書き戻し前 | 書き戻し後 |
|---|---|---|
| グラフ名 | `claude/2026-04-30` | **`claude/2026-04-30`（同一）** |
| cognomen | `"Marcellinus"` | `"Marcellinus Corrected"` |

再投入で同名グラフが置換されれば、旧値は Fuseki からも消える。
「旧値は Fuseki に残るので実害はない」という §4.10 時点の認識は誤りだった。

### 4.11.2 既存語彙の調査

新規オントロジーは**不要**だった。`epig_ontology.ttl:31` が
`owl:imports <http://www.w3.org/ns/prov-o#>` を宣言済みで、PROV-O 全体が利用可能。

| 必要な概念 | 語彙 | 従来の使用 |
|---|---|---|
| 版であること | `prov:Entity` | ✅ グラフに使用中 |
| 「○○の一時点の姿」 | **`prov:specializationOf`** | ❌ 未使用 → 今回採用 |
| 無効になった時刻 | **`prov:invalidatedAtTime`** | ❌ 未使用 → 今回採用 |
| 無効にした行為 | **`prov:wasInvalidatedBy`** | ❌ 未使用 → 今回採用 |
| 旧版への接続 | `prov:wasRevisionOf` | ✅ Statement で使用中 |
| 生成した解釈行為 | `hmkia:generatedBy` | ✅ 定義上 EntityReference も対象 |

当初案の `hmkia:SupersededValue` は不要。標準語彙のみで表現でき、
外部ツールが解釈できる利点もある。`hmk_ontology` 側の変更は発生しなかった。

### 4.11.3 設計 — 現在値と履歴を分離

案E（§4）の失敗原因は「層のトリプルだけで現在値を再構成しようとした」こと。
そこを分ける。

- **現在値**: 従来どおり `claude/{extract日付}` に全属性を書く
  → クエリ無変更、null 問題なし、性能劣化なし
- **旧値**: `{edcsId}/history` グラフに追記のみ
  → 碑文単位の固定名なので再投入で置換されない

```turtle
GRAPH <.../graph/EDCS-25501631/history> {
  <.../entityref/EDCS-25501631/person/1/cognomen/0>
      a                      prov:Entity ;
      prov:specializationOf  <.../entityref/EDCS-25501631/person/1> ;
      epig:cognomen          "Marcellinus" ;
      hmkia:generatedBy      <.../activity/extract_career_graph-...> ;
      prov:generatedAtTime   "2026-04-30T14:06:48Z"^^xsd:dateTime ;
      prov:wasInvalidatedBy  <.../activity/apply_editor_json-manual_edit-...> ;
      prov:invalidatedAtTime "2026-10-07T05:10:37Z"^^xsd:dateTime .
}
```

### 4.11.4 実装

| ファイル | 変更 |
|---|---|
| `_provenance_utils.py` | `record_superseded_value()` を追加。旧値を `_provenance.value_history` に退避 |
| `export_corrections_to_json.py` | 上書き前に履歴を記録。`manual_edit_activity_id()` を切り出し |
| `create_rdf_himiko.py` | `build_history_graph()` を追加。`value_history` から history グラフを生成 |

**enrich 側は変更不要だった。** 全7パスが `'field' not in person` /
`if 'x' in benef: continue` で既存値を保護しており、上書きが発生しない。

### 4.11.5 検証

| 項目 | 結果 |
|---|---|
| 旧値が `value_history` に退避される | 生成元 act（extract）まで正しく記録 ✓ |
| RDF として妥当 | rdflib で 772 quads をパース、history 7 quads ✓ |
| 現在値と履歴が別主語・別グラフ | `person/1` と `person/1/cognomen/0` ✓ |
| **claude グラフを DROP しても旧値が残る** | history グラフに残存 ✓ |
| 2回目の校訂で履歴が連鎖 | `cognomen/1` → `wasRevisionOf` → `cognomen/0` ✓ |
| 完全な系譜を SPARQL で辿れる | 値・有効期間・生成 act を取得 ✓ |
| 校訂のないレコード | history グラフを出力しない（回帰なし）✓ |

検証はすべて一時データセット `proto_hist` で実施し削除済み。
本番 Fuseki（5,214,616 トリプル）は無変更。

### 4.11.6 制約

**遡及は不可。** 過去に enrich が上書きした値は復元できない。
`career_graphs` / `validated_career_graphs` / `modified_career_graphs` の
差分から部分的に再構成できるが（§3.4 はその方法）、act 単位の粒度には届かない。

保証されるのは**今後生成・更新されるデータ**についてのみ。
