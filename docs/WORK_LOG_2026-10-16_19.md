## 1. 統制語彙の整備

3フィールドとも全件パース（サンプリングなし）で棚卸しし、病理が異なることが
判明したため、それぞれ別の方針を採った。

| | object_type | social_status | position_abstract |
|---|---|---|---|
| 現行の種数 | 40 | 91 | 659 |
| 主な病理 | 粒度の不統一 | **多軸の混在** | **称号と役職の混在** |
| 第1階層の統制 | なし | なし | **既にあり（10種）** |
| 採った方針 | 2階層に再設計 | 多値配列（案C） | 主要52種のみ統制 |

### 1.1 社会的身分を多軸にした理由

同一軸内に複数の値が明示されている人物が112件あった。軸ごとに固定スロットを
置く設計（案B）ではこれを表現できず、現在の単一値フィールドの問題を軸の数だけ
増やして再現することになる。`epig:SocialStatusStatement` を介した多値とした。

役職は `career_path` に委ね、宗教は「役職」と「立場」で分割した。
`career_path` との重複率がそのまま役職らしさの指標になっていた
（pontifex 100% / martyr 0%）。

### 1.2 官職を全件統制しなかった理由

659種は object や social_status と違い役職名そのものであり、ローマの官職は
本来多様である。5件未満が485種あるが合計783件（3.8%）に過ぎない。
「発散」ではなく「実態」の面があるため、主要52種（89.7%）のみとした。

## 2. 調査で判明した落とし穴

### 2.1 evidence が当該人物以外を指す場合がある

`social_status_evidence` から追加の軸を機械的に拾う規則を試作したところ、
`social_status='emperor'` の人物に `legal.slave` が付く誤りが18件発生した。

```
social_status: 'emperor'
evidence     : 'Aug(usti) ser(vus)' ＝皇帝の奴隷
```

evidence は「この人物の身分の根拠」とは限らず、同じ碑文の他の人物への言及を
含む。**正規表現マッチだけで軸を追加してはならない。**
`status_category_map.json` の `evidence_rules` は `enabled: false` とした。

詳細: [SOCIAL_STATUS_INVENTORY.md §4-7](../network_analysis/SOCIAL_STATUS_INVENTORY.md)

### 2.2 medicus と Medicus は同綴異義

`medicus`(32) は「医師」、`Medicus`(14) は Marcus Aurelius の**勝利称号**。
小文字化による一括統合は誤分類を生む。`position_canonical_map.json` を
`case_insensitive: false` とし、個別に列挙した。

### 2.3 decurio は同綴異義（都市参事会員 / 騎兵小隊長）

585件中、evidence から判別できたのは都市参事会員144件・騎兵4件のみ。
**437件は文脈でしか決まらない**ため LLM 判定が必要。

### 2.4 stale な派生物

`coverage_report.json` が `object_category_map.json` より8日古く、
数値が食い違っていた（needs_llm 962 vs 845）。生成物の鮮度は
生成元の更新日と突き合わせて確認する必要がある。

## 3. 校訂フローの再設計

### 3.1 問題

従来は校訂が `JSON → RDF → JSON` と往復していた。書き戻しが滞ると次の
enrichment が未校訂値に対して走り、再取り込みで機械グラフがタイムスタンプ
勝負に勝ってしまう（`export_corrections_to_json.py` の docstring が自ら
述べていた）。JSON が単一の真実であるべきなのに、往復の途中だけ別の真実が
存在する構造だった。

加えて、エディタは `SPARQL_UPDATE_ENDPOINT` に `DELETE WHERE` を直接
発行しており、設計意図（ブラウザから直接書かない）と実装が乖離していた。

### 3.2 新しい構成

```
validated_career_graphs (JSON)   ← 単一の真実
        ↓ 読み込み（地名単位）
   ai_epigraphy_editor           ← 別リポジトリ
        ↓ 差分ファイル
   edits/pending/ → apply_edits_to_json.py → edits/applied/
        ↓
validated_career_graphs (JSON)
        ↓ create_rdf_himiko.py
      Fuseki (RDF)               ← 派生物。一方向
```

競合検出は Fuseki の `prov:generatedAtTime` から、差分の `old_value` と
現在値の照合に置き換えた。エンドポイントに依存せず JSON だけで完結する。

旧スクリプト2本は、Fuseki に人手校訂が1件も残っていないことを確認した
うえで削除した（`hmkia:InterpretationAct` 0件）。

## 4. Fuseki の置き換え

```
DROP ALL        HTTP 204 / 1秒未満
```

### 4.1 検証

| 項目 | 結果 |
|---|---|
| provenance グラフ | 2,196,623 triples（投入前 2,169,359） |
| `positionType` | 全件 URI 化（文字列ゼロ） |
| `objectCategory` | 17,970 |
| `socialStatusCategory` | 22,443 |
| `positionCanonical` | 20,259 |

tier 別の集計が SPARQL で通ることを確認した
（title 5,716 / senatorial 4,527 / priesthood 3,835 …）。

### 4.2 【重要】バックアップは取得していない

ユーザ判断によりバックアップなしで実行した。結果としてデータは失われて
いないが、**この投入は取り消せない**。

バックアップ取得は3回失敗した。原因は curl の `--max-time` が
ダウンロード完了前に接続を切っていたことで、サーバ側の問題ではない。
同じ理由で `DROP ALL` も初回は 504 になった（タイムアウトを外したら
1秒未満で成功）。

**次回以降、Fuseki に対する長時間の操作ではタイムアウトを付けないこと。**
934MB のダンプに約25分、446MB の投入に約18分かかる。
