## 2. 判断 — DEPCHA モデルを採用しない

### 根拠

実データ 18,802 件の恵与を調査した結果:

| 指標 | 件数 | 比率 |
|---|---|---|
| 永続・反復の定型句（`in perpetuum`, `quotannis` 等） | 91 | 0.48% |
| 利子・元本の語彙（`usura`, `reditus`, `sors` 等） | 81 | 0.43% |
| `construction`（建築） | 9,042 | 48.1% |

Transaction / Transfer / Account の三層は、元本と果実が分離して時間をまたぐ
**基金碑文（fundatio）でこそ意味を持つ**が、該当するのは 0.5% 未満。
残りでは Transaction が Transfer を一つ包むだけの、情報を持たないラッパーとなる。

「誰が、誰に、何を」は三項関係であり、単一ノードに 3 つの述語を付ければ表現が完結する。
複式簿記が解くのは勘定間の残高整合であって、三項関係ではない。

### 旧実装の問題点

1. **`recurrence` に根拠のない `once` を無条件付与** — 18,000 件超。碑文は省略的であり、
   反復性への言及がないことは一度限りを意味しない。不明と偽の混同。
2. **`derivedFrom` がほぼ発火しない** — 基金碑文の核心である元本→果実の連鎖が、
   別スロットに分かれて抽出されるためリンクされない。
3. **`BenefactionAccount` が機能していない** — Transfer から Account への参照がなく、
   複式簿記の要である借方・貸方の接続が欠落。

### 保持したもの

`fundingType` / `fundingEvidence` / `recurrence` は恵与の性格を決める重要属性のため、
`BenefactionStatement` に移設して保持。

## 4. エディタの修復

### 4.1 判明した問題

エディタは **HIMIKO 対応前の旧スキーマ**を前提に書かれており、読み書きとも機能していなかった。

| エディタが使う語彙 | Fuseki 上の件数 |
|---|---|
| `a epig:Person` | **0**（正: `epig:PersonReference` 84,081） |
| `a epig:Community` | **0**（正: `epig:CommunityReference` 12,592） |
| `epig:mentionedIn` | **0** |
| URI `/person/{edcsId}/{id}` | **0**（正: `/entityref/{edcsId}/person/{id}`） |

碑文を開いても人物が 1 件も表示されない状態だった。

### 4.2 読み取りの修正

`editor/editor_script_sparql_v2.js` のクエリ 5 本を修正:

- クラス名: `Person` → `PersonReference`、`Community` → `CommunityReference`、
  `Relationship` → `RelationshipStatement`
- 結合: `epig:mentionedIn` → URI 接頭辞フィルタ、
  `hasCareerPosition` → `CareerStatement` + `epig:subject`、
  `hasBenefaction` → `BenefactionStatement` + `epig:agent`
- プロパティ名: `position`→`positionText`、`object`→`objectText`、`cost`→`costOriginalText`、
  `sourcePerson`/`targetPerson`→`source`/`target`、`notes`→`evidence`、
  共同体の `rdfs:label`/`normalizedName`→`hmki:surfaceForm`/`normalizedForm`
- **バージョン対応**: Statement は `_v0`〜`_v3` の連鎖を持つため最新版のみ取得
- **リテラル/URI の取り違え**: `socialStatus`・`divinityType` は
  `STRAFTER(STR(?uri), "status/")` で URI から切り出していたが実際はリテラル値

検証（EDCS-25501631）: 全クエリが 0 行 → 5〜10 行を返すようになった。

### 4.3 書き込みの方式変更

ブラウザから Fuseki へ直接書き込むには資格情報を JS に埋め込む必要があり、
公開サーバでは安全に扱えない（`/update` は認証なしで 401）。

**エディタは編集差分 JSON を書き出し、認証済みの別プロセスが反映する**方式に変更。

```json
{
  "format_version": "1.0",
  "edcs_id": "EDCS-25501631",
  "editor": "junogawa",
  "base_version": {
    "graphs": ["...graph/EDCS-25501631/claude/2026-05-03"],
    "retrieved_at": "2026-10-06T23:39:00Z"
  },
  "edits": [{
    "subject": "...entityref/EDCS-25501631/person/1",
    "subject_type": "PersonReference",
    "predicate": "epig:cognomen",
    "old_value": "Marcellinus",
    "new_value": "Marcellinus(訂正)",
    "datatype": "xsd:string"
  }]
}
```

URI は**取得時に保持した実 URI をそのまま使う**（組み立て直さない）。
これが URI 不一致の再発防止になる。

## 5. 人手校訂の記録方式（`99881f3`）

`pipeline/provenance/apply_editor_json.py` を新規作成。

### 5.1 reification を使わない

本プロジェクトは既にバージョン連鎖（`prov:wasRevisionOf`）で履歴を管理しており、
人手編集だけ reification にすると来歴の記述が二系統に分かれる。
`epig_ontology.ttl` にも「旧スタイル: バージョン付き Statement + prov:wasRevisionOf に移行済み」
との記載がある。

### 5.2 リソース種別で記録方法を分ける

| 種別 | 方式 | 理由 |
|---|---|---|
| Statement（career/benefaction/relationship） | 後続 URI `_vN` を発行し `prov:wasRevisionOf` で接続 | 末端ノードで参照が少なく波及しない |
| **EntityReference（person/community）** | **URI を変えず、editor グラフに層化** | 多数の Statement から参照されるハブ |

**EntityReference をバージョン化しない理由**（検討の経緯）:

`person/1` 一つに対し **278 本の参照**（`epig:agent` 232、`epig:source`/`target` 46）が存在する。
人物全体では `hmki:references` だけで 172,282 本。
新 URI を発行すると既存参照がすべて旧版に取り残され、
「この恵与を行ったのは誰か」を辿っても修正が反映されない。
参照を張り替えれば Statement 自身も変更されたことになり、連鎖的に波及する。

→ URI は不変とし、**名前付きグラフを版の単位として扱う**。

### 5.3 新しさの判定 — `prov:generatedAtTime`

EntityReference 自身は `hmkia:generatedBy` を持たない（84,081 件すべて 0）。
しかし**グラフ自体が `prov:Entity` として生成来歴を持つ**ため、グラフ経由で時刻を辿れる。

```turtle
<.../graph/EDCS-25501631/claude/2026-05-03>
    a                          prov:Entity ;
    prov:wasGeneratedBy        <.../activity/extract_career_graph-...> ;
    prov:wasDerivedFrom        <.../graph/EDCS-25501631/edcs/2026-01-15> ;
    epig:interpretsInscription <.../inscription/EDCS-25501631> .
```

**56,635 グラフすべてで取得可能**（欠落なし）。グラフ名の文字列解析は不要。

```sparql
PREFIX epig: <http://epigraphic-careers.org/ontology#>
PREFIX prov: <http://www.w3.org/ns/prov#>

SELECT ?value ?when WHERE {
  GRAPH ?g  { ?person epig:cognomen ?value }
  GRAPH ?gm { ?g prov:wasGeneratedBy ?act }
  GRAPH ?ga { ?act prov:generatedAtTime ?when }
} ORDER BY DESC(?when) LIMIT 1
```

> **追記 2026-10-07**: `apply_editor_json.py` の競合検出だけがこの方針から外れ、
> グラフ IRI の文字列ソートで最新を判定していた。
> [WORK_LOG_2026-10-07.md](WORK_LOG_2026-10-07.md) §1 で修正。

実測（2 回の校訂を適用した状態）:

| 値 | 確定時刻 | 出典 |
|---|---|---|
| Marcellinus-B | 2026-10-06T15:26:57Z | editor/...2657Z |
| Marcellinus-A | 2026-10-06T15:26:56Z | editor/...2656Z |
| Marcellinus | 2026-05-03T09:25:48Z | claude/2026-05-03 |
| Marcellinus | 2026-04-30T14:06:48Z | claude/2026-04-30 |

### 5.4 生成されるデータ

```turtle
GRAPH <.../graph/EDCS-25501631/editor/20261006T152657Z> {

  # グラフ自体の来歴（機械抽出グラフと同形式）
  <.../graph/EDCS-25501631/editor/20261006T152657Z>
      a                          prov:Entity ;
      prov:wasGeneratedBy        <.../activity/editor/20261006T152657Z> ;
      epig:interpretsInscription <.../inscription/EDCS-25501631> ;
      prov:wasDerivedFrom        <.../graph/EDCS-25501631/claude/2026-05-03> .

  # 校訂行為
  <.../activity/editor/20261006T152657Z>
      a                      hmkia:InterpretationUpdateAct ;
      hmkia:hasType          "manual_edit" ;
      hmkia:hasDate          "2026-10-06"^^xsd:date ;
      epig:activityType      "manual_edit" ;
      prov:wasAssociatedWith <.../agent/editor_B> ;
      prov:generatedAtTime   "2026-10-06T15:26:57Z"^^xsd:dateTime ;
      hmkia:revises          <.../activity/editor/20261006T152656Z> .

  # 校訂者（LLM と型で区別）
  <.../agent/editor_B> a hmkia:HumanAgent ; rdfs:label "editor_B" .

  # 校訂された値（URI は元のまま）
  <.../entityref/EDCS-25501631/person/1>
      epig:cognomen     "Marcellinus-B" ;
      hmkia:generatedBy <.../activity/editor/20261006T152657Z> .
}
```

- 連続する校訂は `hmkia:revises` で連鎖し、順序と参照関係が明示される
- 適用前に格納値と `old_value` を照合し、読み込み後に別処理が同じ箇所を
  更新していた場合は中断（`--force` で上書き可）
- 既存参照 278 本は**無変更のまま**校訂後の値に到達することを実データで確認

## 6. 重複グラフの扱い — 残置

同一碑文が複数回抽出され、日付違いのグラフが併存している。

| 指標 | 件数 |
|---|---|
| 重複碑文 | 4,688 |
| 複数グラフに現れる人物 | 6,890 / 77,100（8.9%） |

### 削除しない理由

最新グラフのみを採用すると、**1,340 碑文で 1,987 主語が失われる**。

| 失われる主語 | 件数 |
|---|---|
| relationship | 1,960 |
| benefaction | 13 |
| career | 8 |
| person | 5 |
| community | 1 |

| 性質 | 件数 |
|---|---|
| 別バージョンが最新に存在 | 1,259 |
| **最新に全く存在しない** | **728** |

98.6% が relationship。`reextract_relationships` で再抽出した際に
**抽出される関係が減った**碑文があり、旧グラフにしかない関係が存在する。
LLM の再抽出は改善とは限らず、どちらが正しいかはデータだけでは決められない。

→ **グラフは残し、表示時に最新を選ぶ**方針とした。

### クエリ側の対応

`latestGraphOnly()` ヘルパーを追加し、読み取りクエリ 5 本に適用。

```sparql
GRAPH ?__gm { ?g prov:wasGeneratedBy ?__act }
GRAPH ?__ga { ?__act prov:generatedAtTime ?__t }
FILTER NOT EXISTS {
    GRAPH ?__g2 { ?person a epig:PersonReference }
    GRAPH ?__gm2 { ?__g2 prov:wasGeneratedBy ?__act2 }
    GRAPH ?__ga2 { ?__act2 prov:generatedAtTime ?__t2 }
    FILTER(?__t2 > ?__t)
}
```

検証（EDCS-25501631）: 全クエリで行数＝一意主語数となり重複表示が解消。

| クエリ | 修正前 | 修正後 |
|---|---|---|
| personQuery | 8 | **5** |
| benefQuery | 10 | **9** |
| career / community / rel | 8 / 5 / 5 | 8 / 5 / 5 |

## 付録: 論文記述用の整理

更新の記録方式について、論文に記述できる形の説明は本作業中に別途作成した。要点のみ:

- reification を使わず、バージョン付きリソース + `prov:wasRevisionOf` で記録する
- 解釈行為は `hmkia:InterpretationCreationAct`（19,739 件）/
  `hmkia:InterpretationUpdateAct`（112,380 件）で型付け
- `prov:qualifiedAssociation` + `hmkia:ExecutorRole` で主体の役割を明示（133,576 件）
  - ただし `hmkia:ResponsiblePartyRole`（学術責任者）は**定義のみで実データは 0 件**
- 人手校訂は `hmkia:HumanAgent` として LLM（`SoftwareAgent`）と型で区別
  - ただし**実データとしての校訂はまだ 0 件**（実装済み・未運用）

論文では「実装した」と「運用した」を区別して記述すること。
